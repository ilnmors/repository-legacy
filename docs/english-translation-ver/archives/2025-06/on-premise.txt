An on-premise home network project for personal use
The goal of this project is to build an on-premise home network for personal use with equipment and a network layout that are available at home, and through it to understand deeply, and learn by doing, how many technical elements (networking, operating systems, virtualization and containers, resource management, databases, running production-grade services, security) come together on a network and work as one system.

1. Project overview

1.1. Motivation and goals
Motivation

 The project began as a search for a way to store my personal photos and data. The first option was a cloud service. But with the cloud, the provider can always access the data it holds. That means no complete control over my own data and no full ownership of it. To solve this, my first choice was to set up a NAS (Network Attached Storage). After setting it up, though, the NAS also abstracted away much of its configuration and use, so the same problem remained. If I cannot configure and handle my data freely while using it, I thought, this is no different from the cloud, or even riskier.

 So I decided to move beyond a simple NAS and set the goal of building an on-premise environment where I hold every right and responsibility for my personal data. An on-premise environment built by one person will hardly guarantee the availability and stability of a commercial service. Through this project, however, I want to build it myself and gain understanding and experience of the essential components of modern IT (Information Technology) infrastructure, how they interact, and the environment itself. Another goal is not to be the weakest link myself when using IT services and networks.

 During my military service I managed a battlefield network: a large on-premise environment with distributed regional networks and triple-redundant physical HA (High Availability). I want to bring into this project what I ran back then: complex manuals that were hard to understand, structures designed around SoC (Separation of Concerns), an automatic backup system based on LTO (Linear Tape Open) and systematic recovery scenarios. Beyond the past experience of simply typing commands and operating by the manual, I set and want to achieve the goals below.

 Combine abstract, separate concepts from several fields such as operating systems (OS), networking and information security, and build them for real. Along the way, understand in detail how the concepts connect and work. Through this I want to develop a feel for how theory can be implemented and applied in practice. Rather than building every part of the stack myself, separate the core of the infrastructure from the parts that can be delegated while staying under control. By focusing on the essentials and delegating with control kept in my hands, I want a division of labour that raises the technical quality and maintainability of the whole project.

 Solving problems and overcoming constraints

 The project will run into many technical and environmental problems that were not foreseen. When they occur, I want to learn to stay calm, analyze them precisely, and find and apply solutions based on technical grounds.

 Systematic documentation and knowledge management

 Documentation matters most in every part of the project. By documenting every step systematically in BookStack (plans, designs and their reasons, build procedures and logs, settings, records of solved problems), I want to go beyond a one-off build and turn knowledge and experience into an asset I own, manage and can share.

 Conclusion

 This project does not aim at a perfect infrastructure design from the start or a build without errors and trial and error. The value I want from it is not just building an IT environment one person can use and learning technologies. The project itself, and the failures and trial and error along the way, will be good lessons too. The ultimate value and goal is to build the thinking and execution needed to solve problems, and to reach the level where I can design and control a stable service, even on a small scale, and run it stably.

 Review

 Server hardware

 Building it myself

 Low-power processors for 24/7 operation are mostly sold soldered onto a board. So even when building a server myself, there is less freedom than assembling a PC. On top of the board and processor there is also the cost of a case and the various interfaces.

 Off-the-shelf products

 Off-the-shelf products often offer specialized features at a low price and good quality. For low-power processors in particular, a ready-made product gives better quality for the price than building one.

 Conclusion

 I chose Aoostar's WTR Pro as the server hardware: among ready-made products it included every interface the project needs.

 In absolute terms the R7 5825U is far faster than the N150: twice the cores, four times the threads and a much higher clock speed. Given the project's requirements, though, the N150 is enough. I expect the N150 may not always stay responsive under heavy load the way the R7 5825U would, so resource allocation needs particular care when the services run.

 24/7 operation

 For 24/7 operation the processor must be low power, low heat, quiet and stable. The R7 5825U performs much better than the N150, but it draws more power and runs hotter. Its TDP is roughly 2.5 to 4 times higher, which means more heat and power use when it runs 24/7 at home. That would also affect the stability of the system considerably.

 Price

 The R7 5825U model costs about 30% more than the N150 model, roughly 120,000 KRW extra.

 Other considerations

 

 The R7 5825U model had these known hardware issues:

 

 Some workloads (transcoding and others) were reported less stable than on the N150.

 The SATA controller was reported to misbehave when passed through on a hypervisor.

 With the mini PC's limited cooling and four HDD bays, heat was reported not to dissipate easily.

 

 

 The R7 5825U model has one more RAM slot and one more M.2 slot than the N150 model.

 Conclusion

 The R7 5825U is far more powerful than the N150. But given the project's requirements (light IPS/IDS operation, web, media and application services for a few people, very little transcoding and very unlikely concurrent load), the N150 will be enough to reach the goals. This is the key point: if load beyond the requirements is assumed, even a very powerful server processor with plenty of RAM can run short. Every hardware choice must balance performance against requirements. Weighing that balance, stability, price and the other considerations, I chose the N150 model.

2.2. Network design
Goal

 

 Identify the physical and hardware limits in the network design and choose technical ways to overcome them.

 Identify the potential risks of the final network design and plan how to respond to failures.

 Record the considerations and reasons for each step clearly.

 

 Requirements

 

 Identify and work around the constraints of the home's physical cabling.

 Since the main network devices lack VLANs, find ways to secure L2 traffic end to end and isolate clients.

 Monitor and control inbound and outbound traffic centrally with a firewall and IPS/IDS.

 Understand the difference between L2 and L3 traffic clearly and define security measures for each.

 

 Review

 Physical network diagram

 

 Physical constraints

 

 No power in the terminal box, so the base network devices use PoE (no new node can be added)

 A single physical line between each room and the terminal box

 The main network devices (T5004, AX6000M, H5008G) do not support VLANs, so VLANs cannot be applied to clients outside PVE

 The T5004 does not support DHCP relay, so OPNsense cannot run DHCP and subnetting cannot be used

 

 Dual-gateway structure

 Constraints

 For OPNsense to be the gateway and run DHCP, it would have to sit in the terminal box or use DHCP relay. The lack of power in the terminal box rules out the first. The T5004 supports neither VLANs nor DHCP relay, which rules out the second. So OPNsense cannot run DHCP itself and act as the gateway.

 Workaround and conclusion

 Since the T5004 lets its DHCP server hand out a different default gateway, set OPNsense as the DHCP default gateway of the T5004's untagged VLAN. OPNsense itself gets a static IP and uses the T5004 as its own gateway, which gives a dual-gateway structure. The expected risk is:

 If OPNsense's IP is not static, it may name itself as its gateway and cause a routing loop

 As long as OPNsense has a static IP and does not take its address from the T5004, there is no routing loop risk. At the same time, all L3 traffic passes through OPNsense. Since the OPNsense firewall cannot sit physically right behind the T5004, this dual-gateway structure is the most practical way to control L3 traffic.

 The servers and services inside PVE can use VLANs through vmbr, so a routing table has to be written with OPNsense's routing.

 

 Untagged VLAN to untagged VLAN: unicast through ARP

 Untagged VLAN to other VLANs: OPNsense is the internal gateway, so OPNsense routes it

 Untagged VLAN to WAN: OPNsense is the internal gateway, so OPNsense routes it to the T5004

 Other VLANs to WAN: OPNsense is the internal gateway, so OPNsense routes it to the T5004

 

 OPNsense NIC layout

 Constraints

 Two physical NICs can be given to OPNsense, and the T5004 does not support LACP (Link Aggregation Control Protocol). Under these conditions the design goal was to handle WAN traffic on NIC0 and LAN (including VLAN) traffic on NIC1 to minimize bottlenecks, with all L3 traffic controlled centrally by OPNsense.

 Workaround and conclusion

 

 To solve this I considered the two options in the diagram below.

 

 Merge NIC0 and NIC1 into vmbr0 and connect it to vtnet0 in OPNsense, managed as a single interface

 Assign NIC0 and NIC1 to vtnet0 and vtnet1 and manage them separately

 

 Option 1 manages a single interface and IP for the untagged VLAN in OPNsense, so the setup is simple, and with active-backup it handles a NIC failure automatically even without LACP. But it cannot separate WAN and LAN traffic onto different NICs, which was a project goal: traffic reaches OPNsense through a single vtnet, and vmbr0, a virtual L2 device, does not distinguish NICs. With active-backup only one physical NIC is used normally, so traffic cannot be spread effectively across the NICs.

 Option 2 connects each physical NIC to its own vmbr, assigns both to OPNsense and manages them as separate interfaces with separate IPs. Through OPNsense's L3 interfaces, WAN traffic and LAN traffic can take separate physical NIC paths. Firewall rules can then be applied to vtnet0 and vtnet1 individually for precise control, and both physical NICs are used actively. The setup is more complex than option 1, though. Each physical NIC becomes a SPOF whose role stops if it fails. And without explicit routing policies, asymmetric routing can cause network failures.

 I finally chose option 2 for these reasons:

 

 It makes the difference between L2 and L3 traffic clear and gives a deeper understanding of OPNsense routing, firewall policies and interface management

 It implements the original design goal, WAN on NIC0 and LAN (including VLANs) on NIC1, explicitly at L3

 It actively uses two separate physical NICs, which helps performance

 It makes the dual-gateway structure explicit

 

 Client firewall policies under zero trust

 Constraints

 The T5004 and the other home network devices support neither VLANs nor subnets. That means clients outside PVE cannot be flexibly separated into logical L2 networks. LAN traffic is L2 traffic: it passes neither the L3 firewall (OPNsense) nor the gateway. In L2 traffic, a client learns the target's MAC address through an ARP broadcast and talks to it by unicast. Without VLANs and subnetting, ACLs (Access Control Lists) cannot be managed through the firewall. That raises the need for security measures inside the internal network. Clients inside PVE, however, can be separated at L2 with VLANs.

 Workaround and conclusion

 Traffic must be encrypted with WPA3 so outsiders cannot easily join the network. There are no VLANs, but the T5004's guest network can isolate the network that visitors use: it blocks LAN traffic and allows only WAN traffic.  ACL policies inside each VLAN (including the untagged VLAN) must be handled on the clients. Under zero trust, each server's and client's own firewall (iptables, Windows Firewall and so on) must be set strictly so that, by least privilege, only the required ports and IPs are allowed. A home network has few servers and clients to manage, so these measures should stay manageable without becoming overly complex. Server configuration automation tools such as Ansible can also reduce the management burden.

 Splitting the servers' and clients' ranges into VLANs so that OPNsense, an L3 device, handles all their traffic would solve this more reliably. In particular, OPNsense can control directly which IPs reach VLAN 2, 3 and 4 inside the WTR Pro, so I will try these policies:

 

 Restrict which internal IPs can connect (specific client IPs)

 From outside, access only through the VPN

 Only certain services (reverse proxy and others) are open to everyone, as far as their purpose requires

 

 I confirmed that OpenWRT can be installed on the T5004. After building the on-premise environment as planned, I can test OpenWRT on the T5004 and VLANs across the whole network. Going beyond VLAN separation to a DMZ (Demilitarized Zone), however, is a different matter: a home network cannot be monitored 24/7 and cannot run a CERT (Computer Emergency Response Team). A DMZ could then add management points and vulnerabilities instead. So even in the OpenWRT project I will not run a separate DMZ.

 Traffic security and encryption

 Constraints

 For WAN traffic, a TLS certificate from an external CA makes encryption fairly easy. Internal traffic, however, cannot be encrypted with external TLS certificates.  Some weak protocols used on the internal network (NFS, SMB and others) cannot use TLS and send plain text, so a way to encrypt them is needed. Certain LAN protocols cannot be used from the WAN, so a VPN is needed as well.

 Workaround and conclusion

 By default, the T5004 opens through NAT only HTTPS (443) for web services and the VPN port. That blocks port scans and similar threats from the WAN against the LAN, and it also reduces OPNsense's load.  Blocking direct access by IP from the WAN, allowing access only by domain, using Cloudflare's DDoS protection and routing every web service through the reverse proxy should make WAN traffic safer still. On the T5004 itself, the external admin page should be blocked, every weak feature such as UPnP disabled, strong passwords used and the firmware kept current.

 To encrypt LAN traffic as well as WAN traffic, I want to build an internal CA (TLS encryption) with FreeIPA and an authentication structure with Kerberos (encryption of NFS, SMB and others, and the basis for SSO later). Kerberos can also serve LDAP and SSO in the long run, so FreeIPA is built as one integrated system. When building FreeIPA, it is also important to write scripts that automate signing, issuing, renewing and revoking certificates for internal domains with the internal root CA.

 FreeIPA includes its own DNS, so I want a local DNS that implements split-horizon DNS, giving access through the same domain from outside and inside. AdGuard Home can block ads and malicious domains and integrate with FreeIPA. Requests for domains not in the local DNS are forwarded to a trusted external DNS, Cloudflare's public DNS over DoH.

 Avoid managing internal servers and clients over the WAN; when needed, manage them through the VPN. LAN services (AdGuard Home and others) are also used only after connecting to the LAN through the VPN.

 The SPOF (single point of failure) problem

 Constraints

 OPNsense and FreeIPA are the most important services on the home network. If they fail, the whole network can stop even when all other hardware is fine.

 

 OPNsense: gateway + firewall + VPN server

 FreeIPA: internal CA + internal DNS + KDC

 

 L2 traffic, MAC-based unicast through ARP, still works when they fail, but once outbound and inbound traffic stops, the availability of the home network takes a fatal blow.

 Workaround and conclusion

 The best solution would be physical HA by scaling out, but the budget does not allow it now. The project's goal is also learning and experience rather than matching a commercial service, so some compromise on the SPOF problem is needed. To avoid the problem as far as possible I looked at these measures:

 

 Back up the OPNsense and FreeIPA settings (each service's own features plus Gitea and Ansible)

 Snapshot-back up the VMs with Proxmox's features

 Send alerts from the monitoring server when something goes wrong (mail cannot be sent while outbound/inbound traffic is down)

 Check each VM's state periodically from Proxmox, restart it automatically on a problem and restore it from a snapshot if the problem persists

 

 If these measures run as automated scripts, the RTO (recovery time objective) should stay minimal and the RPO (recovery point objective) manageable.

 Traffic between VMs, LXCs, Docker and clients

 PVE can give each VM/LXC a Linux bridge (vmbr) and a vNIC (vtnet), and Docker can communicate over its internal bridge through dockerd.

 With these, I want to isolate the server network and the special-purpose networks (Kali and the practice LAN) with VLANs in OPNsense, using vtnets and vmbrs not connected to a physical NIC. Every VLAN uses OPNsense as its gateway.

 Docker uses macvlan to give a container its own IP address only in special cases. Otherwise containers talk over the host's internal bridge network and, for external traffic, through the host's IP address and ports.

 Conclusion

 This review suggests that the desired functions and structure can be built despite the real physical and hardware constraints. The constraints can be worked around, but the limits do not disappear, so thorough policies, steady monitoring and logging, and adjustment remain necessary. Through this process I want to understand in depth when and how each protocol works and the overall structure of network communication.

 The final network design is summarized in 1.3, Final target architecture.

  Besides strong security and stability, convenience weighs heavily in a VPN. Especially where the VPN is used mostly from mobile devices, low battery use, split tunneling and easy, intuitive client setup improve the experience greatly. All three protocols offer strong security and stability, so I chose WireGuard, which uses the least battery and is the most intuitive and easiest to set up.

 Conclusion

 What matters most in this project is how much I can learn. Using an existing NAS OS as the file server might be more convenient than configuring it myself. But considering integration with the other services, the limited hardware and the learning value, I concluded that building the file server myself is better than a NAS OS.

 So I compared Ubuntu and Debian (stable) as the OS for the server, leaving out NAS OSes. Both are stable and light, but PVE, the hypervisor, is based on Debian, so I chose Debian for consistency with the other LXCs and VMs.

 The default file system will be Btrfs, which provides its own deduplication, CoW and snapshots. CoW can cause external fragmentation, though, so periodic defragmentation and compression have to be used.

 For the cloud service for personal file management, what matters most is low resource needs and specialization. The other functions besides file management (PIM, multimedia and so on) will be built separately with Docker on the application server when needed. So, comparing Nextcloud and Seafile, I chose Seafile, which specializes in file management, over the feature-rich Nextcloud.

 Finally, for the backup service that preserves the file server's files, I again considered learning value and ease of use.

 Duplicati is a file backup system that has been used for a long time, but it lags the others in support for modern deduplication algorithms and offers less powerful CLI functionality.

 BorgBackup is also a long-established and powerful system and uses the strongest, most modern deduplication algorithm. It allows fine-grained management through its CLI, but it has no GUI without a separate tool called Vorta, and it falls short in conveniences such as backend integration.

 Kopia has not been around long, but it is developing quickly. It supports modern deduplication algorithms and offers both a CLI and a GUI. It also integrates many backend systems (including third-party cloud services) on its own.

 Weighing all of this, I chose Kopia as the one that meets both learning value and ease of use.

 Seafile and Kopia are both deployed with Docker so they run in a consistent environment.

 So the file server will run Seafile + Kopia (on Docker) on Debian (stable, netinst).

 Database, web and application services

 The database, web and application services will be built with Docker on a VM so they behave the same in any environment. Docker is convenient, but rootless Docker has major restrictions (creating internal interfaces and so on), so it has to run with root privileges.

 Docker therefore has to run in a VM, not an LXC. Docker running in an LXC could use root privileges to break out of the LXC into the hypervisor's kernel space. In an LXC, AppArmor/seccomp also make it likely that Docker services fail for lack of privileges. Unprivileged LXCs with rootless Docker can run into the restrictions mentioned above and are not a recommended setup either. So Docker always needs complete logical separation through a VM.

 vmbr 

 

 Works like a virtual L2 switch inside PVE.

 STP 

 STP is a protocol that prevents broadcast storms: when a broadcast occurs between switches, a loop can send broadcast packets back and forth endlessly. A switch without STP therefore cannot have redundant switch-to-switch links. So to put several NICs in one vmbr, STP must be enabled for the network to work. (The recommended way is a bond with LACP.)

 #!/bin/bash

DOMAIN=""

TTL=180 # basic value

C_TTL=86400

PROXIED="false" # basic value

DELETE_FLAG=0

CURRENT_IP=""

FLAG=""

# usage func

usage() {

 echo "Usage: $0 -d \"domain\" [-t \"ttl\"] [-p] [-r] [-c]"

 echo " -d <domain> : Specify the domain to update."

 echo " -t <ttl> : Specify the TTL (Time to Live)."

 echo " -p : Specify the cloudflare proxy to use."

 echo " -r : Delete the DNS record."

 exit 1

}

# using getopts to get arguemnts

while getopts "d:t:pr" opt; do

 case $opt in

 d)

 DOMAIN="$OPTARG"

 ;;

 t)

 TTL="$OPTARG"

 ;;

 p)

 PROXIED="true"

 ;;

 r)

 DELETE_FLAG=1

 ;;

 \?) # unknown options

 echo "Invalid option: -$OPTARG" >&2

 usage

 ;;

 :) # paramenter required option

 echo "Option -$OPTARG requires an argument." >&2

 usage

 ;;

 esac

done

# get option and move to parameters

shift $((OPTIND - 1))

# check necessary option

if [ -z "$DOMAIN" ]; then

 echo "Error: -d option (domain) is required." >&2

 usage

fi

if ! [[ "$TTL" =~ ^[0-9]+$ ]] || [ "$TTL" -le 0 ]; then

 echo "Error: -t option (ttl) requires a number above 0." >&2

 usage

fi

# change directory for cron

cd "$(dirname "$0")"

# make config directory and log directory

if [ ! -d "./config" ]; then

 mkdir ./config

fi

if [ ! -d "./log" ]; then

 mkdir ./log

fi

LOG_FILE="./log/ddns_$(date "+%Y-%m-%d").log"

CONF_FILE="./config/ddns.conf"

# log func

log()

{

 local text="$1"

 echo "---------" >> "$LOG_FILE"

 echo -e "$(date "+%Y-%m-%d %H:%M:%S"): $text" >> $LOG_FILE

}

# check and create log file

if [ ! -f "$LOG_FILE" ]; then

 log "Notice: log file is created"

fi

 Dockerfile and docker-compose.yml

 What a Dockerfile is

 

 A script for building a Docker image, written in this form.

 

 

 # 1. FROM: the base image (required)

# - decides which OS or prebuilt image to start from.

# - e.g. ubuntu:22.04, node:20, python:3.10-slim, mariadb:latest

FROM <base_image>

# 2. WORKDIR: the working directory

# - the path to work in inside the container. Later COPY, RUN and CMD instructions run in this directory.

WORKDIR /app

# 3. COPY: copy files

# - copies files from the host (my computer) into the container.

# - e.g. COPY . . (copy everything in the current directory)

COPY <host_path> <container_path>

# 4. RUN: run a command

# - a command to run while building the image.

# - e.g. RUN apt-get update && apt-get install -y vim (install packages)

# - e.g. RUN npm install (install dependencies)

# - combining them into one RUN reduces build layers and helps keep the image small

# - after installing packages, delete the cache: && rm -rf /var/lib/apt/lists/*

RUN <command>

# 5. EXPOSE: expose a port (documentation only)

# - states which port the container uses. The actual port mapping is done with 'docker run -p' or in 'docker-compose.yml'.

EXPOSE <port_number>

# 6. CMD: the command when the container runs

# - the command run when the container starts.

# - only one per Dockerfile.

# - e.g. CMD ["npm", "start"]

# - CMD and ENTRYPOINT are inherited from the base image as they are.

# - CMD: replaced when docker run is given another command (the default command)

# - ENTRYPOINT: the executable that always runs first, whatever happens

# - they can be overridden if needed, but mostly are left alone.

CMD ["executable", "param1", "param2"]

# 7. ENV: environment variables

# - sets environment variables used inside the container.

ENV <key>=<value> 

 

 

 

 An image built from a Dockerfile cannot know about updates to its parent image, so a label is added in the YAML file and it is managed through Diun.

 

 

 labels:

 - "diun.enable=true"

 - "diun.watch_repo=Original_Image"

 - "diun.watch_tag=latest" 

 

 Once running, the Diun process watches that container.

 Diun can also watch containers on remote servers, but they must be explicitly allowed through iptables. [Docker API default ports: 2375 (plain text), 2376 (SSL/TLS)]

 Plain-text transfer is vulnerable to attack, so SSL/TLS is used.

 

 

 

 docker-compose.yml 

 

 The collection of settings needed to turn a Docker image into a container. It is defined like this.

 

 

 # 1. version: the Compose file version

# 2. services: the list of containers

 # - or the Dockerfile in a given directory

 # build: ./my-app

 

 # 5. container_name: name the container

 container_name: <custom_container_name>

 

 # 6. ports: port forwarding

 # - 'host port:container port'

 ports:

 - "80:80"

 

 # 7. volumes: volume mounts for persistent data

 # - 'host path:container path'

 - ./data:/var/lib/mysql

 - DB_USER=myuser

 # - makes the DB container start first so the Node.js app can run

 depends_on:

 - db

# 10. networks: network settings (optional)

 <network_name>:

 driver: bridge

 

# 11. volumes: volume definitions (optional)

Appendix 1. Document writing guidelines and glossary

Appendix 1.1. Document writing guidelines
Goal

 These guidelines are the reference for improving the quality of this project's documents and writing everything clearly and consistently. They are for a single author, as a personal project, and pursue the following goals for the author and expected readers (technical interviewers and others).

 

 Accuracy: every piece of information is based on fact and written to be easy to understand.

 Conciseness: clear, concise sentences convey the key points.

 Currency: all progress is reflected in the documents so they stay up to date.

 

 Document structure and format

 Heading levels

 Every page uses HTML heading tags such as H1, H2 and H3 consistently to make the hierarchy of the content clear.

 Table of contents

 Managed with BookStack's built-in features.

 Dates

 Dates follow the international standard ISO 8601: YYYY-MM-DD hh:mm:ss.

 Change history

 Separately from BookStack's built-in features, record the change history (date and main changes) in a section separated by a rule at the bottom of the page, for version control. Record changes like this:

 YYYY-MM-DD - summary of the change

 Paragraphs and lists

 One paragraph holds one topic. When listing information, use ordered (<OL>) or unordered (<UL>) lists as appropriate.

 Emphasis and quotes

 Use BookStack's callouts appropriately for quotes, information, success, warnings, danger and so on.

 Tables

 When comparing complex data that is hard to explain in prose, organize it visually in a table (<TABLE>). Use the row header option in tables. In the cell properties, center the text both horizontally and vertically for readability.

 Images and diagrams

 Make visuals with draw.io and upload them as [file_name].drawio.png. Images must be sharp and readable, with captions where needed. When saving the PNG, keep the draw.io data embedded for later editing.

 Code and commands

 Enter code and commands with BookStack's source code feature.

 Links

 Use BookStack's internal and external links so other documents can be referenced quickly. Add internal references with BookStack's own feature, so links stay valid when documents change later.

 Writing style

 Terminology

 Use terms consistently throughout the documents. When a term first appears, give the full name with its abbreviation and define it in the glossary under Appendix 1. After the first use, use the abbreviation, except where emphasis calls for the full name.

 Style

 Write as objectively and clearly as possible in the active voice. Use the passive only when necessary. Write in short sentences, not long winding ones, focused on plans, analysis and results. Use tenses to fit the situation and keep the documents consistent (present tense by default; past or future only where they apply).

 Grammar and typos

 Use terms consistently through the glossary when writing. After writing, proofread to fix awkward grammar and wrong terms.

 Punctuation

 Use periods, commas and the like where they belong, without overusing them, to keep sentences clean.

 Document management

 Review and updates

 When the plan changes during the project, review and fix every related document immediately. Even without changes, check all documents periodically for inconsistencies and fix them.

 Using the to-do list

 During the project, make active use of the to-do list page as a scratch space before content goes into the formal documents. Write there freely, without regard to format or terminology. When content later moves into the documents, rewrite it to the guidelines and delete it from the list.

 Periodic rewriting

 Review and revise the documents once a week to follow the writing guidelines and the glossary.

 Conclusion

 Throughout the project, write clear, consistent and readable documents following these guidelines. This document may also change as the project goes on.

 The pg_hba.conf file

 

 To reapply it, run pg_ctl reload in bash, or SELECT pg_reload_conf(); inside psql

 

 # pg_hba.conf - client authentication settings

# ----------------------------------------------------------------------

# TYPE DATABASE USER ADDRESS METHOD

# ----------------------------------------------------------------------

# TYPE: connection type (local, host, hostssl, hostnossl)

# local: Unix domain socket connections (only inside the container)

# host: TCP/IP connections (with or without SSL)

# hostssl: TCP/IP connections (SSL required)

# hostnossl: TCP/IP connections (SSL not required)

# DATABASE: databases the connection may use (all, sameuser, samenet, replication, specific_db_name)

# all: every database

# sameuser: the database with the same name as the user

# samenet: databases on the same subnet as the user's IP address

# replication: replication connections

# specific_db_name: a specific database name

# USER: users allowed to connect (all, specific_user_name, +group_name)

# all: every user

# specific_user_name: a specific user name

# +group_name: users in a specific group

# ADDRESS: IP addresses or network ranges allowed to connect (IP/CIDR, hostname, all, samehost, samenet)

# IP/CIDR: an IP address with a CIDR mask (e.g. 192.168.1.0/24)

# all: every IP address

# samehost: all of the server's own IP addresses

# samenet: every subnet the server's IP addresses belong to

# METHOD: authentication method (trust, reject, md5, scram-sha-256, peer, ident, gssapi, sspi, cert, pam, ldap, radius)

# trust: allow without a password (very dangerous; test environments only)

# reject: refuse the connection

# md5: MD5-hashed password authentication

# scram-sha-256: SCRAM-SHA-256 hashed password authentication (current recommendation)

# peer: authenticates Unix domain socket connections by matching the OS user name

# ident: authenticates by the client's OS user name

# ldap: authentication through an LDAP server (usable with FreeIPA)

# ----------------------------------------------------------------------

# 1. local connections (psql clients and the like inside the container)

# Unix domain socket connections are often set to 'trust' (no password) by default.

# This is possible only inside the container, so it is relatively safe.

local all all trust

# 2. connections from the host (with Docker 'ports' mapping)

# when connecting from the Docker host to 127.0.0.1 (localhost)

host all all 127.0.0.1/32 scram-sha-256

# 3. connections from the internal Docker network

# when another container on the Docker Compose network (e.g. Infisical) connects to the PostgreSQL container

# check the exact subnet with 'docker network inspect <your_network_name>'

# e.g. 172.18.0.0/16 or 172.17.0.0/16

host all all 172.17.0.0/16 scram-sha-256

# 4. allow a specific VM/physical server on the internal network (example)

# if a VM with the internal IP 192.168.1.100 needs to connect

# host all all 192.168.1.100/32 scram-sha-256

# 5. allow only a specific user on a specific database (finer control)

# e.g. allow only infisical_user on infisical_db from the internal Docker network

# host infisical_db infisical_user 172.18.0.0/16 scram-sha-256

# e.g. allow only the admin account (postgres_admin) on every database from a specific IP range

Appendix 3. Troubleshooting

[2025-05-06] MariaDB and BookStack containers cannot run
Goal

 Solve MariaDB and BookStack containers failing to run in the Container Manager package of DSM 7.1 on a Synology DS124

 Symptoms

 

 The MariaDB container fails to create the database and the BookStack container fails to start

 Container Manager shows them as running normally

 The MariaDB container's logs show Permission denied

 The BookStack container's logs show DB connection failed

 The MariaDB container cannot be reached from the BookStack container's shell

 

 What was tried

 

 First assumed a problem with MariaDB's accounts and database, so connected to the container shell and created the database and account BookStack uses by hand

 How to open a container shell in DSM's Container package: DSM Container Manager > Container > container name > Action > Open terminal > Create to get inside the container

 

 BookStack still could not connect to MariaDB

 To check whether TLS was the problem, checked that TLS connections were not used (have_SSL DISABLED)

 show variables like '%ssl%';

---

have_SSL DISABLE

--- 

 

 TLS was disabled, so it was not the cause; redeployed the containers and checked the startup logs

 The MariaDB container's logs show Permission denied

 Set the permissions of the directories inside the container (the mounted directories) by hand

 

 Solution

 

 Check the owner of the mounted directories in File Station

 Check that the directory owner is 1000, the MariaDB container's own UID

 But creating the directories in advance assigns the DSM user's ID instead of 1000, so let the container create them itself.

 

 Give the mounted directories owner rwx, then restart the containers

 Confirmed that the MariaDB container runs normally without Permission denied in its logs

 Gave the directories mounted into the BookStack container owner rwx as well

 Confirmed that after BookStack started, the database was created normally in the MariaDB container

 Confirmed that the BookStack service works

 

 Cause

 Synology DSM gives the ContainerManager group rwx on directories that containers mount. MariaDB and BookStack, however, assign their own UID/GID inside the container, and an ACL conflict seems to have arisen there. The owner was UID/GID 1000/1000, but the directory's owner had no permissions, so the directory could not be accessed. That prevented normal database creation and communication. After explicitly giving the directory owner rwx, the problem did not recur.

 Conclusion

 Docker provides a virtualized environment, but dockerd follows the host's permission structure. On special-purpose OSes such as Synology DSM, a less fine-grained permission structure can clash with Docker's. So when running Docker in such special environments rather than ordinary Linux, always check that the owner and permissions of mounted directories match the UID/GID inside the container.

 Also, official documentation and blog guides describe the usual situation. Copying and pasting without understanding each command can cause unexpected errors or conflicts, so when something fails, make a habit of checking basics such as ACLs first and reading the logs carefully.

[2025-06-08] Images in posts inside the BookStack container do not update
Goal

 Solve images in posts not updating in the BookStack container running in the Container Manager package of DSM 7.1 on a Synology DS124

 Symptoms

 

 When editing a BookStack page, the old image is shown even after the image file is replaced

 

 What was tried

 

 Checked BookStack's image upload directory

 Confirmed that the files in the directory (/www/uploads/images/gallary/YYYY-MM) changed

 After confirming the update, opened the page in a browser on another device to check for a cache problem

 The updated image was shown correctly

 After a hard refresh (Ctrl+F5 or Ctrl+Shift+R), the original browser also showed the updated image

 

 Solution

 When page content such as images does not update, clear the cache and do a hard refresh, then check again

 Cause

 A cache stores web pages, images, multimedia and so on temporarily to reduce server latency. When loading a page, the browser fetches the HTML again but reuses files in its cache whose lifetime has not expired, which saves data and is faster. But when those files change, the browser may keep using the cached copies instead of fetching the new ones, so the change does not appear on the page.

 Clearing the cache in the browser settings, or a hard refresh that ignores everything in the cache and reloads, solves this.

 Conclusion

 An error may come from the service itself, or from the client loading it. So when an error occurs, look at it from several angles, including the client and the network, rather than only the service.

[2025-06-19] - 504 Gateway Timeout when clicking Install Gitea on the Gitea container's initial setup page
Goal

 Solve a 504 Gateway Timeout when clicking the Install Gitea button on the initial setup page while setting up the Gitea container in the Container Manager package of DSM 7.1 on a Synology DS124

 Symptoms

 

 After installing the Gitea container, the initial setup page loads normally

 Clicking the Install Gitea button then shows the Synology NAS error "Sorry, the page you are looking for is not found." (404 Not Found)

 The Gitea container log shows no error

 The browser's developer tools show a 504 Gateway Timeout

 

 What was tried

 

 First assumed a problem with MariaDB's accounts and database, so connected to the container shell and checked the database and account Gitea uses

 How to open a container shell in DSM's Container package: DSM Container Manager > Container > container name > Action > Open terminal > Create to get inside the container

 

 After confirming the database and account were fine, connected to the Gitea container shell and checked connectivity with ping

 Checked the permissions of the /docker/gitea/data folder mounted into the container

 After checking everything, looked at Synology's reverse proxy and raised the proxy connection timeout, proxy send timeout and proxy read timeout from 60 to 600 seconds

 

 Solution

 

 Set the proxy connection, send and read timeouts on the reverse proxy long enough

 After the redirect to the initial setup page, retry the Gitea installation

 Confirmed that the installation page works

 

 Cause

 Synology's reverse proxy uses these default timeouts to keep target servers from overusing system resources.

 

 Proxy connection timeout = 60 s

 Proxy send timeout = 60 s

 Proxy read timeout = 60 s

 

 The DS124's limited specs (1 GB RAM, no read/write cache, HDDs) slow down setting up services such as Gitea. When the Gitea installation took more than 60 seconds, the reverse proxy closed the connection to the client automatically, which produced the 504 Gateway Timeout.

 Conclusion

 When using a service, especially a web service, errors such as 504 Gateway Timeout can come from the reverse proxy's settings even when the service and the network are fine. The problem arises when the backend takes longer than the reverse proxy's timeout, and on limited hardware initialization can take longer than expected, so this needs checking.
